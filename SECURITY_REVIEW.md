# Meetly — Security & Privacy Architecture Review

**Product:** Meetly  
**Developer & Maintainer:** Evolix Studio  
**Audit & Review Date:** October 2026

---

## 1. Executive Summary

Anonymous chat and video applications inherently present high-risk vectors for abuse, harassment, underage exposure, non-consensual content, and network exploitation.

This security review outlines Meetly's security and privacy design, defensive hardening measures, and critical policy disclosures. It candidly highlights the technical boundaries and launch requirements that must be understood prior to any broad public release.

---

## 2. Authentication, Session & Token Security

1. **Anonymous Ephemeral Sessions:**
   - Meetly does not require account creation, emails, or phone numbers.
   - Sessions are minted via `createAnonymousSession()` with a cryptographically secure 256-bit identifier (`id`) generated by `crypto.randomBytes(32).toString("base64url")`.
   - The token format is `${id}.${signature}`, where signature is computed using HMAC-SHA256 (`crypto.createHmac("sha256", signingKey)`).
   - Timing-safe equality checks (`crypto.timingSafeEqual`) are used to verify tokens, preventing timing attack leaks.
   - Session lifetime is capped at 3 hours (`SESSION_TTL = 3 * 60 * 60 * 1000`). Expired sessions are purged automatically.

2. **WebSocket Session Authorization:**
   - When a WebSocket connection opens at `/api/chat/live`, it starts in an unauthenticated state with a strict 5-second timeout.
   - The client must send an `{ type: "auth", token: "..." }` message within 5 seconds; failure results in immediate socket termination (`close(4401)`).
   - Only validated sessions receive the active state and room message events.

## 3. Network Security & Transport Controls

1. **WebSocket Origin Validation & CSWSH Defense:**
   - The HTTP upgrade listener in `server/chat/live.ts` inspects the incoming `Origin` header against the configured `CORS_ORIGIN` allowlist.
   - If an unauthorized origin initiates the upgrade request, the connection is rejected with HTTP `403 Forbidden` before WebSocket negotiation begins.

2. **HTTP Security Headers:**
   - In `server/_core/index.ts`, custom security headers are applied to all responses:
     - `X-Content-Type-Options: nosniff`: Prevents MIME-sniffing exploits.
     - `X-Frame-Options: DENY`: Blocks clickjacking and iframe embedding.
     - `Referrer-Policy: strict-origin-when-cross-origin`: Restricts referrer leaks.
     - `Strict-Transport-Security: max-age=31536000; includeSubDomains`: Enforces HTTPS in production.

3. **CORS Restrictions:**
   - Cross-origin HTTP requests are strictly limited to the domains specified in `CORS_ORIGIN`.

## 4. Abuse Prevention & In-Memory Rate Limiting

Meetly enforces multi-tier rate limiting to prevent denial-of-service, spam floods, and bot scraping:

| Target Action             | Limit            | Window     | Scope                   | Failure Handling                       |
| ------------------------- | ---------------- | ---------- | ----------------------- | -------------------------------------- |
| **Session Creation**      | 20 requests      | 60 seconds | Ephemeral IP/Client Key | Rejection with `429 Too Many Requests` |
| **Search / Next Skip**    | 20 requests      | 60 seconds | Per Session             | Rejection with `429 Too Many Requests` |
| **Chat Messages**         | 8 messages       | 10 seconds | Per Session             | Rejection with `400 Bad Request`       |
| **Repeated Content**      | Max 2 duplicates | 30 seconds | Per Session             | Rejection with `400 Bad Request`       |
| **Video Control Signals** | 180 signals      | 60 seconds | Per Session             | Rejection / Signal Suppression         |
| **Safety Reports**        | 3 reports        | 1 hour     | Per Session             | Rejection with `429 Too Many Requests` |

## 5. Content Sanitization & Data Safety Filters

1. **Text Message Scrubbing:**
   - Messages are constrained to between 1 and 500 characters. Whitespace is trimmed.
   - **Link Blocking:** All regular expressions matching `http://` and `https://` URLs are rejected to protect users from malicious links, phishing, and scam domains.
   - **PII Scrubbing:** Regular expressions detect phone numbers and email patterns, rejecting messages containing potential contact details to protect anonymous user identity.
2. **Database Query Safety:**
   - MySQL interactions are handled exclusively via Drizzle ORM using parameterized queries. Zero raw SQL string concatenation is used, eliminating SQL injection vectors.
3. **Database Privacy Guarantees:**
   - Ordinary chat text is **never** written to the database. Room message buffers (capped at 120 messages) exist solely in RAM and are destroyed immediately upon conversation termination or room expiration (2 hours).
   - Only user-initiated safety reports are persisted to the database. The report excerpt is included only when the reporting party explicitly chooses the "Include recent excerpt" checkbox (capped at 6 messages and 1,000 characters).
   - Session identifiers are hashed with SHA-256 before storage in `safety_reports` (`reporterSessionHash`, `reportedSessionHash`).

## 6. Anonymous Video Chat & WebRTC Privacy Considerations

1. **Direct WebRTC vs. Relay Privacy:**
   - Video calling uses direct browser peer-to-peer WebRTC (`RTCPeerConnection`).
   - STUN servers discover peer candidates. In direct P2P connections, each peer's network IP address is exposed to the other peer and the STUN provider.
   - **Mitigation:** The application explicitly warns users in the interface, consent gate, and `/privacy` / `/safety` pages that video is direct, not an anonymizing relay, and will reveal their network IP.
   - **TURN Configuration:** Meetly now supports configurable TURN relay servers (`TURN_SERVER_URL`, `TURN_USERNAME`, `TURN_CREDENTIAL`) through environment variables. Operators can deploy co-located TURN servers (e.g., Coturn) to route media traffic through an intermediary proxy, preventing direct IP disclosure.

2. **Mutual Opt-in Safety Gate:**
   - Video media does not start automatically.
   - Even when selecting "Video" mode, users begin with camera and microphone inactive.
   - Both matched strangers must independently click "Join video" and grant browser permissions.
   - WebRTC signaling messages (`offer`, `answer`, `candidate`) are strictly rejected by the server unless both users have opted in (`room.videoReady.size === 2`).
   - Clicking "End video" immediately halts local tracks, closes the `RTCPeerConnection`, and returns the user to safe text-only communication.

## 7. Operational & Legal Caveats (Crucial Assessment)

> [!CAUTION]
> **Self-Attested Age Gates & Moderation Limits:**
>
> 1. **Age-Gating:** Meetly employs a self-attestation checkbox for age 18+. Self-declaration **does not** constitute legally sufficient age verification in jurisdictions requiring verifiable parental consent or strict adult verification (e.g., UK Online Safety Act, US state age-assurance mandates).
> 2. **Content Moderation:** In this release, there is no automated AI computer-vision scanning or staffed 24/7 human moderation review pipeline attached to the video stream.
> 3. **Launch Recommendation:** Meetly is prepared for private staging and closed evaluation. Prior to opening public unrestricted production registration, Evolix Studio should evaluate jurisdictional compliance, third-party age verification integrations, and a dedicated safety incident review procedure.
